# F01 빠른 OFF/ON Native 검증 후속 설계 — 승인 요청

상태: 설계안만 작성. 아래 후속 구현·실행은 아직 승인받지 않았다. 제품 수치·효과 범위·권한·버전·공개 경계는 변경하지 않는다.

## 1. 확인한 사실

- 최신 제품 checkpoint: `718db577f8241ad296bd55f5bf3e75526cba3c20`.
- master OFF의 기존10ms wet fade 동안 normalizer 이득 유지, 이후10ms unity 복귀를 구현했다.
- 빠른 ON은 계산한 현재 이득에서 옛 예약을 취소한다. analyser/buffer 생성보다 먼저 취소하고, 생성 실패 시10ms unity로 복귀한다.
- 전체1606개 중1605통과·실패0·기존private 증거1skip, 집중55/55 및9개 기반/build/package가 통과했다.
- 이전 G는3rate EQ108/RMS60/전환72와 출력 대조가 통과했으나, 두 창의 Gain을 ramp 완료 전에 읽은 검사 때문에 전체 실패였다. 해당 이력은 최신 제품의 성공 증거가 아니다.
- 최신 M(`F01audio20261015M-5nbQKt`)은44.1kHz 빠른 전환5개 모두 실제 이득/출력이 계산과 일치했다. 단, 실제 이득 예약 시각이 hold 또는 unity 구간에만 놓여 중간 구간을 검증하지 못했다. source 전후 동일·pageErrors0·종료3증명true이며 전체 실패를 보존한다.
- 요청 지연과 실제 이득 예약 시각은 일치하지 않는다. 예를 들어10ms 요청이 실제약20.3ms 뒤에 예약되는 경우가 관측됐다. 고정 지연 하나에 특정 구간을 대응시키는 검사는 안정적이지 않았다.

## 2. 권장 변경 — Native 자극 성립과 제품 출력을 분리

긴 EQ/RMS 행렬 앞에 독립된 짧은 Native 사전계측 단계를 둔다. 같은 production controller·native AudioContext·실제 미디어 소스·원래 automation 시간을 사용한다. 별도 실제 시청 프로필은 사용하지 않는다.

1. 자극 목록·상한을 실행 전에 고정한다. 최대12개로 제한하며 지연값과 시작 위상을 분산하는 유한 행렬을 상세 계획에서 확정한다. 실행 결과를 보고 목록을 늘리지 않는다.
2. 각 자극의 OFF 호출·ON 호출·실제 gain 예약 시각, 옛 reset 구간, 실제 gain·출력·source/timer 수를 전부 기록한다. 시작 위상 변경도 실제 관측 시각으로만 판단한다.
3. 실제 예약 시각으로 hold / reset 중간 / unity를 분류한다. 요청 지연의 이름으로 구간을 추정하지 않는다.
4. **모든** 유효 측정의 이득·출력 비교가 통과하고 세 구간이 실제로 모두 확보된 경우에만 사전계측을 통과한다. 한 건의 출력 불일치도 버리지 않는다.
5. 구간이 미성립하면 `자극 미성립`으로 명시하고 긴 행렬 전에 종료한다. 이를 제품 DSP 오류나 제품 정상으로 단정하지 않으며 전체 수용은 계속 미완료다.
6. 사전계측을 통과한 동일 clean 입력에서 기존 전체 EQ108/RMS60/전환72 및 출력·수명·설치 회귀를 수행한다. 사전계측 결과와 전체 결과의 입력/환경을 연결한다.

## 3. 변경하지 않는 기준

- master dip 비율0.95·연속성1e-6·fully wet peak0.9801·full-scale 초과0 및 기존 고정14/12/18/stress 기준을 유지한다.
- Native 시간을 가짜 시각으로 바꾸거나 제품10ms 전환을 시험용으로 늘리지 않는다.
- production controller를 건너뛰는 primitive 검사를 실제 ON/OFF 통합 증거로 대체하지 않는다.
- 실패한 측정 폐기·성공만 고르기·무제한 재시도·빈 자료를0으로 채우기는 허용하지 않는다.
- 실제 숨김·두 창 독립·원래 Gain·source1·퇴역 callback0 및 종료 증명을 유지한다.
- push/PR·릴리즈·스토어·사용자 Chrome/P09·root dist·의존성/권한 변경은 하지 않는다.

## 4. 잔여 위험과 중지 조건

브라우저/운영체제 스케줄링 때문에 유한 행렬에서도 중간 구간을 확보하지 못할 수 있다. 이 경우 결과를 미검증으로 남기고 다시 사용자에게 수용기준을 문의한다. 이 설계는 통과를 보장하거나 기존 실패를 성공으로 재분류하는 안이 아니다.

승인 요청 범위는 **위 분리 설계의 상세 구현 계획·동일 기존 권한 안의 도구 보완·회귀·새 Native 재검증**이다. 실제 출력 수치나 제품 DSP 알고리즘을 추가 변경해야 한다면 별도 설계·승인을 받는다.
