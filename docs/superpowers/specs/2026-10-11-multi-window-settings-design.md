# 다중 탭과 창의 설정 저장 충돌 방지 설계

작성일: 2026-10-11 (Asia/Seoul)

상태: 2026-10-11 사용자가 설계를 승인했다. 구현 계획 작성 단계이며, 계획과 실행 방식 승인 전에는 저장 경로를 변경하지 않는다.

## 목적과 성공 기준

치지직을 여러 탭이나 창으로 사용하면서 서로 다른 설정 화면을 열어도, 한 화면에서 바꾼 설정이 다른 화면의 오래된 값으로 되돌아가지 않게 한다. 전역 설정은 공유하되 영상, 미리보기, 오디오 자원의 소유자는 각 페이지로 유지한다. 스타일 적용 버튼은 등록이 완료된 CSS를 사용하고, 설정을 연 원래 치지직 탭만 새로고침해야 한다.

사용자가 승인한 방식은 설정 화면이 바뀐 필드만 보내고 기존 백그라운드가 순서대로 병합·저장하는 구조다. 이 문서의 승인은 구현 계획 작성 단계로의 진행이며, 실제 코딩과 배포 승인은 별도다.

성공 기준은 다음과 같다.

- 두 화면의 서로 다른 필드 변경은 모두 남는다. 같은 필드의 충돌은 백그라운드에 도착해 처리된 마지막 값으로 결정한다.
- 열린 화면은 최신 저장값을 반영하되 사용자의 더 새로운 미저장 입력을 오래된 응답으로 덮지 않는다.
- 스타일 등록 실패와 저장 실패를 구분해서 보여준다. 실패했는데 성공 또는 적용 완료로 표시하지 않는다.
- 적용 대상 탭의 ID와 창 ID를 보존한다. 대상이 사라지거나 치지직이 아니면 다른 탭을 대신 새로고침하지 않는다.
- 한 페이지의 종료나 음량 조작이 다른 페이지의 영상·오디오 자원을 종료하거나 조작하지 않는다.

## 현재 코드의 문제와 보존할 동작

`popup.js`는 최초 `getConfig()`의 객체를 보관하고, 입력 때마다 전체 `config`를 저장한다. `styles.js`도 최초 `styles`와 `styleParameters`를 보관해 전체 배열·객체를 저장한다. 두 화면이 같은 초기값을 읽으면 순차 조작만으로도 서로 다른 변경을 덮을 수 있다. 두 치지직 재생 페이지만 여는 것과 두 설정 화면의 쓰기 충돌은 다른 문제다.

`styles.js`는 저장 완료 직후 적용용 버튼을 표시하고 `chrome.tabs.reload()`를 대상 없이 호출한다. `background.js`의 CSS 등록은 별도 비동기 큐에서 실행되므로, 이 버튼은 등록 완료를 확인한 버튼이 아니다. 등록 과정은 모든 동적 스크립트를 해제한 뒤 `styles`를 다시 등록한다.

기존 저장 키 `config`, `styles`, `styleParameters`와 기본값, 한국어·영어 UI를 유지한다. `config.js`의 유효한 범위와 타입을 기준으로 새 입력을 검증한다. `chat-font-size`의 0은 스타일 비활성화, 0이 아닌 값은 활성화라는 현재 관계도 보존한다. 기존에 저장된 알 수 없는 필드는 무관한 설정 변경 때문에 삭제하지 않는다.

페이지의 HLS 인스턴스, 미리보기 캐시, DOM, 타이머, AudioContext 및 미디어 소스는 백그라운드로 이동하지 않는다. `knifeGain`과 `chatWidth`의 기존 영구 선호값은 계속 공유될 수 있으나, 열린 플레이어의 현재 값까지 강제로 동기화하지 않는다.

## 접근 방식 비교

| 방식 | 장점 | 한계 | 결정 |
| --- | --- | --- | --- |
| 백그라운드 단일 작성자와 필드 단위 요청 | 기존 저장 키와 소비자를 유지하면서 변경을 병합할 수 있다 | UI 요청·실패 처리와 백그라운드 수명 대응이 필요하다 | 채택 |
| 설정 화면이 매번 최신 객체를 읽고 직접 저장 | 변경 범위가 작다 | 두 read 이후 두 write가 겹치면 여전히 변경을 잃는다 | 제외 |
| 모든 필드를 별도 저장 키로 변경 | 서로 다른 필드의 덮어쓰기를 줄인다 | 마이그레이션과 모든 소비자 변경이 커지고 연관된 스타일·매개변수의 일관성 문제가 남는다 | 제외 |

## 구성 요소와 저장 소유권

순수한 공통 스타일 목록을 분리해 스타일 UI와 백그라운드가 같은 ID·매개변수 규칙을 사용한다. 현재 `CONFIGS`는 `config.js`를 재사용한다. 공통 검증 규칙은 DOM이나 저장 부작용을 가지지 않는다.

설정 클라이언트는 팝업과 스타일 화면에서만 사용한다. 입력 상태, 전송 중 요청, 최신 스냅샷, 저장 오류를 관리하며 직접 `chrome.storage.local.set()`을 호출하지 않는다.

설정 저장 담당은 기존 백그라운드 안에 둔다. 사용자 변경, 초기 마이그레이션, 스타일 재등록, 적용용 새로고침을 하나의 순서로 처리한다. 현재 초기화에서 수행하는 `resizeChat`, `t` 이전 작업도 이 순서 안으로 옮겨 사용자 쓰기와 경합하지 않게 한다.

이 구조는 저장 API를 다른 확장 코드가 사용할 수 없도록 만드는 브라우저 샌드박스가 아니다. 이 저장 키에 쓰는 모든 프로젝트 코드가 저장 담당을 통하도록 호출 경로와 테스트로 확인해야 한다. 현재 프로필에서 백그라운드가 하나인 구성을 전제로 하며, 새 incognito split 모드나 프로필 간 동기화는 추가하지 않는다.

## 요청과 검증 계약

메시지는 기존 페이지 브리지와 다른 namespace `cheese-knife-settings`, protocol `1`을 사용한다. action은 `get-snapshot`, `patch`, `reload-target`으로 제한한다. 공통 속성은 namespace, protocol, action, requestId이며, patch에는 operations만, reload-target에는 targetTabId와 targetWindowId만 추가할 수 있다. 요청 ID는 최대 128자로 제한한다.

필드 변경은 절대값을 설정하는 연산이다. config 필드의 값, 스타일 ID의 켜짐·꺼짐, 스타일 매개변수 값만 보낼 수 있다. 임의 JSON 경로, CSS, URL, 스크립트, 객체 전체 교체 또는 반전 toggle 연산은 받지 않는다. 한 요청은 최대 64개 연산을 포함하며 연관된 폰트 값과 활성화 상태는 하나의 연산에서 유도한다. 요청 전체를 검증한 뒤에만 저장한다.

boolean과 범위 설정의 타입·유한성·min/max는 현재 CONFIGS를 기준으로 검사하며 잘못된 값을 clamp해 수용하지 않는다. UI의 step은 입력 표시 규칙으로 유지하고 무관한 기존 값의 재양자화에는 쓰지 않는다. `chat-font-size`는 -6부터 16까지의 유한한 수로 검증하며 같은 저장 안에서 0 여부로 활성화를 결정한다.

보내는 쪽의 ID가 현재 확장 ID인지 확인하고, `sender.url`의 protocol·host·pathname이 `chrome.runtime.getURL('popup.html')` 또는 `chrome.runtime.getURL('styles.html')`와 일치해야 한다. 문자열 prefix나 임의 URL의 opaque origin 일치만으로 허용하지 않는다. query는 적용 대상 정보를 담을 수 있지만 권한 판정에는 사용하지 않는다. top-level 설정 문서만 허용하며, 알려진 0이 아닌 frame ID는 거부한다. URL이나 ID가 빠지면 거부한다.

콘텐츠 스크립트도 같은 확장 ID를 사용할 수 있으므로 ID 검사만으로 허용하지 않는다. CHZZK 문서에서 오는 요청은 거부하며, MAIN 브리지에 설정 쓰기 명령을 추가하지 않는다. 알 수 없는 필드·스타일·요청 속성, 잘못된 타입, 범위를 벗어난 값은 저장 전에 거부한다. 요청 correlation ID는 짧은 문자열로 제한하며 권한이나 저장 순서의 근거로 사용하지 않는다.

## 병합과 순서

백그라운드의 listener는 시작 시 동기 등록한다. callback 응답과 `return true`를 사용하는 방식으로 최소 Chrome 121 및 별도 Firefox 패키지의 호환성을 유지한다. 최신 API에서만 가능한 Promise listener에 의존하지 않는다.

처리 순서는 다음과 같다.

1. 요청의 형식과 보내는 문서를 검사한다.
2. 초기 마이그레이션 완료 뒤 직렬 큐에 넣는다. 대기 요청은 최대 64개로 제한하고 가득 차면 명시적으로 busy를 반환한다.
3. 처리 차례에 저장소의 최신 `config`, `styles`, `styleParameters`, `settingsRevision`을 읽는다.
4. 알려진 필드의 연산만 최신 상태에 병합한다. 스타일 배열은 ID 집합 연산으로 처리한다. 요청과 무관한 기존 필드는 보존한다.
5. 변경된 저장 키와 증가한 `settingsRevision`을 한 번의 `storage.local.set()` 호출로 보낸다. 변경이 없으면 불필요한 저장을 하지 않는다.
6. 스타일 연산이면 현재 스타일 등록을 완료하거나 실패 원인을 기록한 뒤 응답한다. config 전용 변경은 저장 완료를 응답하되, 이미 존재하는 CSS 실패를 전체 설정 저장 불가로 확대하지 않는다.

`settingsRevision`은 로컬에 저장하는 기술적 순번이다. worker가 다시 시작됐다고 0으로 되돌리지 않는다. 기존 키가 없으면 초기값 0으로 시작한다. 비정상 값이나 안전 정수 상한에 도달한 값은 조용히 재설정하지 않고 복구가 필요한 상태로 표시한다. 이 순번은 사용자 활동 기록이나 원격 전송용 데이터가 아니다.

읽기 요청도 같은 큐에서 수행해 쓰기 중간 상태를 응답하지 않는다. 여러 키의 API 호출을 임의의 트랜잭션이나 compare-and-swap이라고 주장하지 않는다. 일관성의 전제는 이 키에 대한 프로젝트 쓰기를 한 작성자와 처리 순서로 통합하는 것이다.

최신 값 조회 응답에는 revision, 정규화한 알려진 설정·스타일 값, CSS 등록 상태만 포함한다. 알 수 없는 저장 필드는 병합할 때 보존하지만 UI 응답에는 노출하지 않는다. patch 응답에는 requestId, revision, stored 여부와 CSS 적용 상태 또는 실패 단계를 포함하고 전체 객체로 로컬 입력을 덮지 않는다.

## 열린 화면과 늦은 응답

클라이언트는 저장 이벤트 구독을 먼저 설치한 뒤 초기 조회를 시작한다. `chrome.storage.onChanged`의 local 이벤트는 값 자체를 무조건 화면에 덮는 명령이 아니라 최신 스냅샷을 다시 읽을 신호로 사용한다. 오래된 이벤트가 늦게 와도 그 이벤트의 옛 값으로 화면을 되돌리지 않는다.

최신 스냅샷은 저장 담당을 통해 읽고 `settingsRevision`으로 오래된 응답을 거부한다. 읽기를 시작한 후 더 새로운 저장 이벤트나 사용자 입력이 발생했다면 읽기 결과의 적용 여부를 다시 판정한다. worker 내부에만 존재하는 순번에 의존하지 않는다.

화면마다 전송 중 요청은 하나만 유지한다. 슬라이더의 로컬 표시는 즉시 갱신하되, 전송 중에 들어온 같은 필드의 입력은 다음 전송의 최신 값으로 합친다. 서로 다른 필드도 연산 단위로 합치며 기존 전체 객체를 보내지 않는다.

미저장 입력은 해당 필드에만 임시로 표시한다. ack는 전체 스냅샷을 무조건 덮지 않고 완료한 입력의 표시만 해제한다. 더 새로운 로컬 입력이 있으면 유지한다. 오류 뒤에는 최신 값을 다시 읽고 저장 불가, 저장 여부 불명 또는 CSS 적용 실패를 구분해 표시한다.

## 스타일 등록과 적용 대상

동적 등록은 현재 소유한 ID `styles`만 관리한다. 다른 등록 ID를 모두 해제하지 않는다. 등록이 있으면 `updateContentScripts`, 없으면 `registerContentScripts`, 선택 스타일이 비어 있으면 해당 ID만 `unregisterContentScripts`로 정리한다. CSS 파일명은 공통 스타일 ID 목록에서만 만든다.

백그라운드의 저장 이벤트도 최신 상태를 다시 조정할 신호로만 사용한다. 이벤트에 담긴 오래된 스타일 배열을 큐에 복제해 나중에 등록하지 않는다. 자신의 저장 이벤트가 추가 조정 작업을 만들더라도 실제 최신 목록을 재조회하고 동일 등록은 반복하지 않아, 등록·저장의 무한 피드백이 발생하지 않게 한다.

저장이 성공했지만 CSS 등록이 실패하면 저장값은 되돌리지 않는다. 화면은 저장 성공과 적용 실패를 함께 표시하고 적용용 새로고침을 비활성화한다. 명시적인 재적용 동작에서 최신 스타일을 다시 읽어 등록한다. 오래된 요청의 CSS 목록을 재시도하지 않는다.

팝업은 열릴 때 해당 창의 활성 치지직 탭 ID와 창 ID를 한 번 캡처한다. 스타일 화면의 링크에 이를 전달하고, 적용 요청에서도 같은 대상 정보를 보낸다. 스타일 화면을 단독으로 열거나 대상이 치지직이 아니면 적용 대상 없음으로 표시하며 다른 창의 활성 탭을 추측하지 않는다.

적용용 새로고침도 큐 안에서 최신 스타일 등록 완료를 확인한 뒤 수행한다. `tabs.get(id)`로 현재 URL이 정확한 HTTPS CHZZK origin이며 창 ID가 캡처된 값과 일치하는지 확인하고 `tabs.reload(id)`를 호출한다. 사용자가 탭을 다른 창으로 옮겼다면 대상을 다시 선택해야 하며 몰래 다른 창을 적용하지 않는다. 삭제된 탭, 다른 사이트로 이동한 탭, 등록 실패는 각각 설명하고 중지한다.

저장된 설정은 전역이라는 사실과 이미 열린 다른 탭의 스타일에는 페이지 새로고침이 필요하다는 점을 표시한다. 다른 방송 탭을 자동으로 새로고침하거나 재생을 중단하지 않는다.

## 종료와 실패 복구

큐의 한 작업이 실패해도 다음 작업은 실행한다. 저장 실패 뒤 이전 전체 객체를 복구용으로 다시 쓰지 않는다. 그렇게 하면 다른 화면의 새 변경을 덮을 수 있다.

worker가 저장 후 응답 전에 종료되면 클라이언트는 저장 여부를 모를 수 있다. 요청을 자동 재전송하지 않고 최신 스냅샷을 다시 조회한다. 저장 여부가 불명인 동안 성공 표시와 적용용 새로고침을 허용하지 않는다. 절대값 연산도 오래된 의도를 나중에 재전송하면 새 의도를 덮을 수 있으므로 무조건 안전한 재시도로 취급하지 않는다.

worker 재시작 시 등록 상태와 최신 저장된 스타일을 조정한다. 별도 상시 heartbeat, 새로운 alarm, keep-alive 우회 또는 네트워크 요청은 추가하지 않는다. Chrome용 shared 파일 로드와 Firefox background scripts의 로드 순서는 각각 패키지 검사 대상이다.

## 페이지 복원과 미디어 소유권

BFCache에서 복원되는 페이지는 과거 configPromise만 재사용하지 않고 최신 설정을 다시 읽는다. 읽기가 진행되는 동안 더 새로운 저장 이벤트를 받았으면 늦은 읽기 결과를 폐기한다. 복원 후 현재 DOM 소유권을 재확인하며, 이 과정에서 다른 페이지의 자원을 건드리지 않는다.

여러 페이지의 동시 재생을 금지하는 전역 오디오 락은 도입하지 않는다. 한 페이지의 음량, 음소거, HLS 종료 및 페이지 종료는 그 페이지의 자원에만 적용한다. 전역 기능 OFF는 각 페이지가 새 설정을 받은 뒤 각자의 비동기 요청·재생 시도를 취소해야 한다.

## 반증 조건과 검증

| 조건 | 합격 기준 |
| --- | --- |
| 두 UI가 같은 초기값을 읽은 뒤 서로 다른 필드 변경 | 두 변경이 모두 저장된다 |
| 같은 필드를 반대 값으로 변경 | 처리 순서의 마지막 값이 저장되고 열린 화면도 수렴한다 |
| 초기 읽기, 이벤트, ack를 다른 순서로 전달 | 더 새로운 저장값·로컬 입력을 옛 응답으로 덮지 않는다 |
| 빠른 슬라이더 입력과 다른 UI의 체크박스 입력 | 슬라이더 최종값과 체크박스 변경이 모두 남는다 |
| legacy migration read와 새 사용자 write의 경합 | 같은 큐의 순서로 처리되고 이전 스냅샷을 늦게 재저장하지 않는다 |
| worker가 commit 전 또는 commit 후 ack 전에 종료 | 이전 전체 상태 재쓰기 없이 최신 스냅샷으로 복구하고 불명 상태를 숨기지 않는다 |
| CSS 등록을 지연 또는 실패시킴 | 완료 전에는 reload를 허용하지 않고 실패를 표시한다 |
| 다른 동적 script ID 존재 | 해당 등록이 그대로 남는다 |
| 대상 탭 삭제, 사이트 이동, 창 이동, 다른 창 활성화 | 원래 검증된 탭만 reload하거나 명시적으로 중지한다 |
| CHZZK 콘텐츠 스크립트와 알 수 없는 문서의 요청 | 저장·CSS 등록·reload 부작용이 없다 |
| 두 페이지의 독립 media와 한쪽 종료 | 다른 페이지의 시간·프레임이 계속 증가한다 |
| BFCache A 동안 B에서 설정 변경 | A 복원 시 최신 설정을 받고 오래된 읽기를 적용하지 않는다 |

테스트는 현재 코드의 전체 객체 저장을 그대로 둔 대조군에서 변경 유실을 재현한 뒤 시작한다. 저장 이벤트, 실제 저장 반영, callback 전달 시점을 따로 제어하는 fixture가 필요하다. 저장을 먼저 반영하는 단순 지연 mock만으로 경쟁 조건이 해결됐다고 판정하지 않는다.

Chrome에서는 두 스타일 화면, 두 방송 탭, 실제 두 창, 다른 활성 창, 재시작, 페이지 복원을 별도로 검사한다. 자동 fixture와 실제 설치본의 결과를 구분하고 사용자 설정을 복원한다. BFCache 수용 조건을 만족하지 않아 실제 복원이 일어나지 않았다면 해당 검사는 미검증으로 기록한다. Firefox 패키지 검사와 실제 Firefox 검증도 구분한다.

## 범위 밖과 승인 단계

HLS 파서 보완과 초기 화질 전환, 플레이어 layout 교체, 채팅 root 재결합, 호스트 권한 축소, 개인정보 고지 및 스토어 자료 수정은 별도 작업이다. 이 저장 경로 설계의 승인이나 두 창 재생 통과가 그 작업들의 완료를 뜻하지 않는다.

제품 전체의 프레임워크 전환, 원격 설정 동기화, 새 결제·로그인 흐름, 전체 탭 강제 reload, incognito 정책 변경은 포함하지 않는다. 개인정보처리방침을 제공하는 기존 브랜치와 URL도 변경하지 않는다.

이 설계의 자체 검토는 요청 소유권, 단일 작성자 전제, 늦은 읽기, worker 종료 후 불명 상태, CSS 등록과 reload의 순서, 두 페이지의 미디어 소유권을 중심으로 수행했다. 독립 Astra max 보안 검토를 완료했다고 표기하지 않는다. 사용자 설계 승인을 반영한 구현 계획을 작성했으며, 계획과 실행 방식의 승인을 받은 뒤 테스트 우선으로 구현한다.

## API 참고

sender의 문서 URL과 frame ID, callback 응답 방식은 [Chrome runtime API](https://developer.chrome.com/docs/extensions/reference/api/runtime)를 기준으로 한다. 동적 등록의 조회·갱신·해제는 [Chrome scripting API](https://developer.chrome.com/docs/extensions/reference/api/scripting)를 기준으로 하며, 현재 사이트 문서에 대한 주입을 새 권한으로 확대하지 않는다.
