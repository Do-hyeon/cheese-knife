# 다중 설정 화면과 페이지 복원 검증

날짜: 2026-10-11 (Asia/Seoul)

상태: 설정 화면 간 동기화, 원래 방송 탭만 적용되는 동작, 폰트 0 복원을 실제 설치본에서 확인했다. Astra max 독립 검토의 Important 1건을 수정하고 전체 408개 검사를 통과했다. 일부 실환경 검사는 아래와 같이 미검증이며 제품 전체의 최종 합격이나 릴리즈 준비 완료 판정은 아니다.

## 자동 검사

최종 리뷰 수정 후 현재 작업 사본의 전체 회귀는 408개 모두 통과했다. 설정 관련 제품 코드 9개 파일의 Node 문법 검사, Chrome·Firefox 빌드와 각 패키지 검사가 통과했다. 패키지는 v2.13.3이다. Chrome manifest에 MV2 background.scripts/page/persistent와 Firefox 전용 metadata가 없음을 검사했으며, 실제 확장 오류 화면의 과거 로그 삭제·재발 여부는 아직 확인하지 않았다.

실제 두 popup HTML 문서의 기존 코드에서 두 번째 전체 객체 저장이 arrowSeek false를 true로 되돌리는 실패를 재현했고, 두 styles 문서에서도 left-chat 선택이 사라졌다. 필드별 요청 연결 후 같은 검사가 통과했다. 다음 검사는 생산 모듈과 실제 DOM을 사용하며 Chrome API의 외부 경계만 대체했다.

- 서로 다른 필드의 보존, 최신 입력의 표시, 전송 중 입력 합치기, 단일 변경 요청 슬롯.
- 저장·응답·이벤트의 별도 지연, 낮은 revision/이전 ack 거부, 같은 revision의 CSS 재시도 순서.
- commit 전·후 응답 소실, 10초 timeout, 늦은 callback 무시, busy/write 실패 뒤 자동 재전송 금지.
- 저장 순번 오류와 상한 도달의 repair-required 상태. 이미 저장된 변경은 rollback하지 않는다.
- CSS 저장 실패와 등록 실패 구분, 소유 ID만 등록·갱신·해제, 명시적인 빈 patch 재시도.
- 원래 탭 캡처를 한 번 공유, 캡처 전 링크 이동 차단, 대상 없음·삭제·다른 사이트·다른 창의 적용 중지.
- 초기 설정 전 입력 비활성화, 한국어·영어 오류 상태, 모든 기존 설정·footer·권한 검사 보존.
- Chrome classic importScripts와 Firefox 순차 scripts 로드. worker 전용 의존성이 누락된 패키지 거부.
- persisted pagehide/pageshow에서 이전 읽기를 무효화하고 새 읽기를 기다리는 동안 오래된 값을 적용하지 않음.
- stale 저장 이벤트 payload를 최신값으로 간주하지 않음. 잘못되거나 사라진 font parameter의 네 소유 CSS 속성 제거.
- 두 실제 runtime/미리보기/오디오 모듈의 독립성, 전역 preview/livePreview OFF 시 각 페이지의 pending 작업 취소, 한쪽 종료 후 다른 쪽 자원 유지.

미디어 fixture는 HLS 및 Web Audio 브라우저 API 경계만 대체한다. jsdom의 currentTime을 조작한 것은 실제 디코딩·재생 시간 증가나 음질을 인증하는 검사가 아니다. 2026-10-11의 이전 두 실제 창 재생 결과는 별도 startup 검증 문서에 있으며, 새 설정 저장 경로의 설치본 검증을 대신하지 않는다.

## 설치본 관찰과 미검증 항목

사용자가 로컬 시험판 확장 새로고침 완료를 알렸다. 이후 공개 방송 두 개를 새 검사용 탭에서 열었다. 한 탭의 재생 시간은 18.01→62.14→98.50초로 진행했으며, 다른 탭은 40.01초에서 첫 탭 종료 후 57.38→69.57초로 진행했다. 각 관찰에서 paused=false, readyState=4였고 페이지 경고·오류 로그는 없었다. 사용자가 설정을 조작하는 동안 두 페이지의 font offset 갱신도 관찰했다. 이는 실제 두 탭 결과이며 동시에 보이는 두 창 검사나 미리보기 음질 검사는 아니다. 검사용 두 탭만 종료했으며 기존 사용자 시청 탭은 건드리지 않았다.

도구가 chrome-extension:// 설정 화면 접근을 명시적으로 거부했다. 우회하지 않고 사용자 수동 검사로 전환했다. 처음 사용자가 한 창의 변경이 다른 창에도 적용된다고 답했으며, 이는 의도한 전역 설정 동기화다. 서로 다른 항목의 확인을 추가 요청한 뒤 사용자는 “꼭 저 옵션이 아니더라도 서로 동기화가 잘되는것 확인”이라고 답했다. 수동 동기화 확인으로 기록하되, 정확한 변경 항목·font 순서·원래 값 복원을 명시적으로 확인한 결과로 확대하지 않는다.

리뷰 수정본 확장 새로고침 후 새 검사용 방송 탭에서 폰트 offset 0→8→0을 직접 관찰했다. 본 방송은 24.97→67.48→141.96초로 재생이 진행했고 paused=false, readyState=4, 페이지 경고·오류 로그 없음이었다. 광고 중 잠시 나타난 player 미준비 상태는 본 방송 재생 후 ready로 바뀌었다. 사용자는 적용용 버튼의 대상에 대해 “원래 방송 탭만 정상 적용됨”이라고 확인했다. 다른 방송 창을 자동으로 새로고침하지 않고, 일부 스타일은 그 창을 직접 새로고침해야 반영되는 동작은 승인된 설계와 일치한다.

임시 변경한 설정의 복원 여부를 추가 질문한 뒤 사용자가 “복원 완료”라고 확인했다. 이후 빠른 폰트 0→8→12→0 조정과 저장 오류 여부를 요청한 검사에 사용자는 “잘되는듯?”이라고 답했다. 이 결과를 정상으로 보인다는 사용자 수동 관찰로 기록한다. 현재 방송 탭에서도 폰트 0, Gain 0.8, configuration·player·compressor ready를 읽기 확인했다. 입력 사이의 시간이나 저장 UI를 도구가 직접 측정한 결과로 확대하지 않는다. 실제 worker 재시작 및 최소 Chrome·Firefox 설치 검사는 여전히 미검증이다. 로드된 확장 파일의 해시도 직접 확인하지 못했으므로 아래 값은 빌드 파일의 해시다. BFCache 수용과 두 창 관찰은 다음 후속 결과로 갱신한다.

## 실제 페이지 복원과 두 창 후속 검사

검사용 방송 탭만 CHZZK 홈으로 이동한 뒤 뒤로 가기를 수행했다. 메인 frame의 `Page.frameNavigated`에서 원래 방송 URL과 `BackForwardCacheRestore` type을 직접 관찰했다. 이 type의 의미는 [Chrome의 공식 Page 프로토콜](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Page.pdl)을 기준으로 한다. 이벤트 buffer에 truncated=true가 있었으므로 이전 사건이 모두 기록됐거나 BFCache 실패 사건이 전혀 없었다고 주장하지 않는다. 복원 후 폰트 0과 configuration ready를 확인했다. 숨겨진 동안의 설정 변경을 동반한 복원은 이번에 실검사하지 않았으며 자동 fixture 결과와 구분한다.

복원 직후에는 광고 영상만 재생됐고, 다른 탭을 연 뒤 첫 탭은 hidden·paused 상태였다. 명시적 재생 버튼 클릭은 대상이 없어 실행되지 않았다. 사용자가 두 탭을 서로 다른 Chrome 창으로 나란히 배치한 뒤에는 양쪽 main player·compressor 상태가 ready였고, 두 본 방송이 모두 visible·paused=false·readyState=4·error=null로 관찰됐다.

| 방송 창 | 기준 재생 시간 | 두 창 관찰 종료 | 원래 Gain |
| --- | --- | --- | --- |
| 햇살살 | 283.156516초 | 361.325641초 | 0.8 |
| 햄쿠비 | 225.605733초 | 303.776793초 | 0.8 |

기준과 종료에서 각 방송의 blob source가 같았다. 약 78초 간격의 기준·중간·종료 표본이며 매초 표본이나 모든 중간 끊김이 없었다는 인증은 아니다. 양쪽 페이지의 수집된 warning/error 로그는 비어 있었다. Gain의 실제 range 입력에서 첫 창을 0.8→0.85로 한 단계 변경하자 첫 창만 바뀌고 다른 창은 0.8을 유지했다. 즉시 0.8로 복원했고 두 창 재생은 계속 진행했다. 이 결과는 현재 Gain 표시·페이지 독립성 검사이며 물리적 출력 음질 검사는 아니다.

첫 검사용 탭만 종료한 뒤 남은 창은 같은 source에서 303.931733→331.038125초로 진행했고 visible·paused=false·readyState=4·error=null, Gain 0.8, 폰트 0, player·compressor ready를 유지했다. 기존 사용자 시청 탭은 조작하지 않았다. 최신 전체 자동 검사도 408/408, 실패·취소·skip 0이다.

첫 창의 포커스 보정 해제는 실제로 성공했다. 두 번째 창의 해제는 문서 응답 대기 제한으로 실행되지 않았고 browser 창 관리 명령도 지원되지 않았다. 따라서 두 창은 사용자 분리·배치 확인과 DOM의 visible·1278×1248 크기 관찰로 인정하되, 양쪽 포커스 보정을 끈 엄격한 조건까지 통과했다고 기록하지 않는다. 실제 영상 프레임 수와 로드 파일 해시는 접근 제한으로 직접 확인하지 못했다. 브라우저 전체나 확장 설정 화면으로 접근을 우회하지 않았다.

## 한계와 범위

[Astra max 최종 검토](../reviews/2026-10-11-multi-window-settings-final-review.md)는 설정 전용 고정 커밋 범위를 검사했다. 응답 대기 중 추가 스타일을 적용 완료로 기록하는 Important 1건을 재현했다. broker가 해당 reload 작업의 `appliedStyles`를 응답하고 UI는 이를 기준으로 사용하도록 수정했다. 새 검사 4개가 먼저 실패했으며, 수정 후 집중 38/38과 전체 408/408이 통과했다. 첫 수정 후의 배열 비교 오류는 jsdom과 Node의 배열 realm 차이였고, 값을 Node 배열로 옮겨 동일한 리터럴 내용 검증을 유지했다. 재검토는 수행하지 않았으며 실제 설치본의 같은 타이밍 재현은 아직 확인 전이다.

tabs.get의 origin/window 검사와 tabs.reload 사이의 사용자 이동을 원자적으로 잠그지는 않는다. 다른 활성 탭을 대신 고르는 동작은 없다. 모든 프로젝트 설정 writer가 단일 broker를 사용하는 전제이며 외부 코드의 직접 저장까지 트랜잭션으로 보장하지 않는다.

HLS 후보 보완과 독립 보안 검토는 별도 미완료 범위다. 이 자동 검사 통과를 보안 검토 완료나 스토어 정책 전체 인증으로 확대하지 않는다. 기존 개인정보처리방침 브랜치·URL은 변경하지 않았으며 PR·push·스토어 제출·릴리즈는 이번 단계에서 수행하지 않았다.
